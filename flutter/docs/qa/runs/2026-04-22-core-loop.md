### Findings

**F1 — DailyLaunchOverlay doesn't re-trigger after DB-only reset.** Wiping `user_daily_rewards.last_claim_date` and cold-launching the app did NOT bring back the overlay. The overlay state is cached in SharedPreferences; DB reset alone is insufficient. Implication for QA: reset scripts in `manual-test-plan.md` must combine DB wipe + SharedPreferences wipe (or Settings › Reset Daily Loop).

**F2 — Muhāsabah multi-question sequence NOT triggered on fresh-today state.** With `current_streak=0` + no prior check-in today, the Home CTA goes: gacha → preview → AI reflection → story → dua → complete. There are no Q1/Q2/Q3 answer screens. Row written with `q1="discover"`, `q2/q3/q4=""/null`. Either the multi-question path only activates on non-fresh states, or it's been simplified. Plan's "answer each muhasabah question" step doesn't match observed UX.

**F3 — Known gacha Continue bug reproduced live.** First tap on Continue (logical `(201, 773)`, center of the button) registered nothing. Second tap on overlay background at `(201, 400)` dismissed it. Code ref: `lib/features/daily/widgets/name_reveal_overlay.dart` — Continue `Container` missing `GestureDetector`.

**F4 — Token balance UI is stale.** After check-in completed, Home shows `1004` in token pill while DB shows `1059`. Either the pill reads from a different cache or refresh never fired post-muhasabah. Visible in `/tmp/sakina-A-10-home-after.png`.

**F5 — `user_daily_rewards` not touched by muhasabah flow.** DB row still `current_day=0, last_claim_date=null` after complete loop. Yet Home bottom banner shows "Day 1/7 claimed" — SharedPreferences-side state advanced but Supabase row did not. Same local/remote drift pattern as F1.

**F6 — `user_activity_log` empty for today.** Expected an entry after check-in; got zero rows.

**F7 — Daily quest not progressed.** `user_quest_progress` where `cadence='daily' and period_start=current_date` returned no rows.

**F9 — Off-topic classifier is too lenient.** The AI gracefully found a spiritual angle ("Ar-Razzaq provides sustenance") on a clearly non-spiritual prompt. Plan's D1 invariant ("off-topic → no usage decrement") is structurally untestable when classifier never fires. Implications:
- Free-limit burns on non-reflective usage
- OpenAI cost burns on pizza-recipe-style prompts at scale
- No guardrail against cost abuse via bot/non-Muslim test usage

**Recommendation:** tighten the off-topic prompt/classifier. Consider adding a threshold of "spiritually relevant" keywords or explicit refusal for recipe/weather/code-style queries.

## B6. Streak freeze auto-consume — BLOCKED

**Seed:**
```sql
update public.user_daily_rewards
set streak_freeze_owned = true, last_claim_date = (current_date - 2)::date, current_day = 7
where user_id = '<uid>';
```

Cold-launch → no DailyLaunchOverlay, no streak prompt. Home shows normally (Lv 3 Repentant, streak 1). `user_daily_rewards` row unchanged after launch (`streak_freeze_owned` still true). `user_streaks.last_active` still 2026-04-22 from earlier A test.

**Finding (extends F1):** The freeze-consume code path at `daily_rewards_service.dart:453` (`consumeStreakFreeze()`) runs inside `claimDailyReward()` when `lastClaimDate != today AND lastClaimDate != yesterday AND streakFreezeOwned`. This path is only reachable when the user proceeds through the DailyLaunchOverlay claim step. Because the overlay gate reads local SharedPrefs first, a server-side seed alone cannot exercise the freeze logic in QA.

**Workaround paths for future testing:**
- Uninstall + reinstall the app between states
- Use Settings › Danger Zone › "Reset Daily Loop" to wipe local state BEFORE seeding (the app may re-hydrate from server on next claim)
- Instrument a debug-only SharedPrefs reset hook callable from a test route
