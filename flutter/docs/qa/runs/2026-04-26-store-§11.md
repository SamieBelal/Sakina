## Summary

Doc spec was stale (Free/Premium tabs, token-priced items). Reality: Tokens/Scrolls tabs, all real-money IAP. Phase 1 caught a P0: `PurchaseService.purchase()` returned `entitlements.active.containsKey('premium')` for consumables, so non-premium users paying for tokens received nothing. Fixed by splitting the API into `purchaseSubscription()` and `purchaseConsumable()`. Regression pinned, 8 widget tests added, full suite green.

## Phase 1 — Bug fix

`lib/services/purchase_service.dart`:
- Removed `purchase(Package)` (the bug site).
- Added `purchaseSubscription(Package)` → returns `bool` for `entitlements.active['premium']`. Used by paywall.
- Added `purchaseConsumable(Package)` → trusts RC's throw-on-failure / return-on-success contract: `await Purchases.purchasePackage(package); return true;`. Used by Store. Simplified to trust the contract; eliminated a theoretical silent-failure path.

## Bug history (preserved here for future regression hunting)

Pre-2026-04-26 `purchase()` body:
```dart
Future<bool> purchase(Package package) async {
  _assertInitialized();
  final customerInfo = await Purchases.purchasePackage(package);
  return customerInfo.entitlements.active.containsKey('premium');
}
```

For consumables, `entitlements.active` is empty after purchase (RC behavior — consumables don't grant entitlements). Therefore `purchase()` returned `false`, `_buyTokensIAP` skipped `earnTokens(amount)`, and the user's local balance + `user_tokens` Supabase row never updated. Apple charged the card, the app delivered nothing. Premium-active users were unaffected because `entitlements.active['premium']` was already true, masking the bug.

Confirmed via `purchases_flutter-8.11.0/lib/models/customer_info_wrapper.dart:24-28`: `CustomerInfo` exposes `nonSubscriptionTransactions: List<StoreTransaction>` and `allPurchasedProductIdentifiers: List<String>` for consumables; entitlement state is independent.

## Out-of-scope findings — verified and fixed (post-/review)

The /review adversarial pass surfaced four pre-existing concerns. After verification, three were fixed in this PR and one was dismissed.

**#1 Refund clawback for consumables — FIXED.** Pre-fix: webhook handler had 0 mentions of REFUND; `earn_tokens` RPC has no transactionId param; no clawback path. User could buy → spend → refund and keep the tokens.

Fix landed:
- New SQL migration `20260427000000_consumable_clawback.sql`: adds `consumable_clawback_events` table (idempotent on `transaction_id`) and `clawback_consumable_grant(p_user_id, p_sku, p_kind, p_amount, p_transaction_id, p_event_timestamp)` RPC. Decrements balance/scrolls clamping at 0; tracks deficit for support reconciliation. Service-role only.
- `revenuecat-webhook/handler.ts`: new `CONSUMABLE_SKU_TO_AMOUNT` map (mirrors Flutter's), new `buildConsumableClawback` builder that detects CANCELLATION events with consumable SKUs, new `clawbackConsumable` option in `HandleWebhookOptions`. Subscription CANCELLATION (with premium entitlement) still routes through `upsertSubscription` unchanged.
- `revenuecat-webhook/index.ts`: wired the new RPC call.
- 10 new Deno tests in `index.test.ts` covering: each builder branch, consumable refund routes through clawback path, subscription CANCELLATION still routes through upsertSubscription, RPC failure → 500 (RC retries).
- Live SQL smoke run on dev DB: `185 → 85` after first clawback (delta -100), idempotency holds on second call (no double-decrement), deficit case caps at balance and records `clawback_deficit=415` in audit table.

**#2 Orphaned consumable on app kill — FIXED.** Pre-fix: `main.dart` initialized RC but never registered a `customerInfoUpdateListener` or called `syncPurchases`. If the app died between `Purchases.purchasePackage` and `earnTokens`, the user paid and got nothing.

Fix landed:
- New service `lib/services/consumable_grants_service.dart`: SKU→amount map, atomic `markCredited(transactionId)` compare-and-set on a SharedPreferences-backed credited set (capped at 200), `processCustomerInfo(customerInfo)` for the listener path, `grantForMostRecentPurchase(productId)` for the synchronous purchase path, `initializeForUser(customerInfo)` baseline on first signin.
- `main.dart`: registers `Purchases.addCustomerInfoUpdateListener` after RC init; calls `Purchases.syncPurchases()` to flush pending receipts.
- `app_session.dart`: calls `ConsumableGrantsService().initializeForUser(...)` after `setUserId` so the listener doesn't re-grant the user's lifetime history on first signin.
- `store_screen.dart`: `_buyTokensIAP` and `_buyScrollsIAP` route through `grantForMostRecentPurchase` to share dedup with the listener — whichever wins the compare-and-set wins the grant.
- 13 new tests in `test/services/consumable_grants_service_test.dart`: dedup primitive, scoped-per-user isolation, 200-entry cap, token grants, scroll grants, idempotency across listener fires, mixed sync-then-listener race, unknown SKU safety, baseline-without-grant, baseline idempotency, post-baseline orphan recovery.

**#3 Subscription false-negative on backend lag — FIXED.** Pre-fix: `purchaseSubscription` returned `false` on first `entitlements.active` miss with no retry. User would see "purchase failed" on a successful purchase and risk double-charge attempts.

Fix landed:
- `purchase_service.dart`: on first miss, falls back to `Purchases.getCustomerInfo()` once and re-checks the entitlement. Throw on the fallback returns `false` (does not propagate, treated as genuine failure).
- 3 new tests in `purchase_service_test.dart`: stale-then-fresh succeeds, both-stale fails, fallback throw doesn't corrupt failure UX.

**#4 `_purchasing` flag survives parent rebuild — DISMISSED.** Investigated via code reading. State preservation is a Flutter framework guarantee for same-type-same-position widgets. The StoreKit dialog is modal — no navigation or rebuild can occur during a pending purchase in production. The "rebuild" would have to dispose+recreate `StoreScreen`, which can't happen mid-purchase. Not reproducible. Filed under "investigated, not a real bug" — no fix needed.

## Out of scope / observations to file

1. **`_IapItem` narrow-width overflow** — the inner Row containing `[title, badge]` overflows when total width is ≤400 logical px. Reproducible at iPhone SE class. Fix: wrap the Row in `Wrap` or shorten "Best Value" copy. Test viewport bumped to 500 to bypass.
1a. **Restore-snackbar position collision** — the SnackBar fires from the link at y=749, but the bottom nav starts at y=784. The default Material SnackBar (~48 px tall) cannot fit in 35 px and is clipped or instantly dismissed. Lift to root `ScaffoldMessenger`, or move the link inline higher up.
2. **`_PurchaseToastWidget` Future-based dismissal** — `Future.delayed` is fine but harder to cancel cleanly than an `AnimationController`. Cosmetic.
3. **Manual `_buyTokensIAP` / `_buyScrollsIAP` near-duplication** — 70 LoC duplicated. Could collapse to `_buyConsumable<T>(amount, productId, label, color, icon, grant: () async => earnTokens(amount))`. DRY win, separate PR.
4. **Sim sandbox StoreKit smoke** — happy-path purchase + post-purchase token grant must be verified on physical device before TestFlight. Widget tests cover the wire-up; only the device confirms RC ↔ App Store ↔ Supabase round trip.
